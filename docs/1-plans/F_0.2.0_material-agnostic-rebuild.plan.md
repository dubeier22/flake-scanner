# Material-Agnostic Flake Scanner — Package Rebuild Implementation Plan

## Overview

Rebuild the single-file `flake_finder.py` prototype into a proper Python
package (`src/flake_scanner/`) that detects 2D-material flakes of a
user-specified thickness on full-chip microscope mosaics, in a
**material-agnostic** way. The rebuild adds a calibration database keyed by
material + substrate + thickness, a **Notion-guided mosaic calibration**
importer that turns the lab's existing AFM datasets into scan-domain color
signatures, and detection improvements (data-driven per-channel weighting,
local substrate sampling). The driving milestone is **hBN detection working
end-to-end** on a real chip-A mosaic, built on the new architecture rather
than bolted onto the old script.

## Problem Statement

The current tool works but has structural limits that block the lab's goals:

1. **Single-material, single-substrate by assumption.** `calibration_data.csv`
   has no `material`/`substrate` columns; the code implicitly assumes
   graphite on 285nm SiO₂/Si. hBN (yellow/gold/green signature, purple
   substrate) cannot be represented alongside graphite.
2. **Calibration is fully manual.** Every calibration flake requires opening
   the viewer, navigating, and pressing F/B — the lab has an extensive
   existing AFM dataset (147 hBN flakes in Notion) whose thicknesses are
   already known and should not be re-derived by hand.
3. **Detection channel weighting is hardcoded-uniform.** `score_region()`
   treats R/G/B equally (modulo std), but the graphite findings show green
   is reliable and blue is not — and which channel is informative differs
   per material. This must be learned from calibration data, not baked in.
4. **One 531-line script** mixes viewer, calibration I/O, and detection math,
   with no tests — fragile ground for the above features.

### Key data-domain constraint (drives the calibration design)

The lab's per-flake AFM crops are **high-magnification** images with a
**beige/tan** substrate and burned-in measurement annotations. The
full-chip **mosaics that will actually be scanned** have a **purple/blue-grey**
substrate. This is the same substrate/white-balance shift that made
`contrast_B` flip sign in the graphite work. Therefore **calibration color
must be sampled from the mosaic** (the scan domain), not from the crops.
The Notion dataset supplies the ground-truth thicknesses and which flakes
were measured; the mosaic supplies the color. (User decision: "Mosaic,
guided by Notion.")

## Solution Architecture

A `src/flake_scanner/` package with clear stage separation, built and
validated in three phases so a working hBN scan is reached without
short-cutting the foundation:

- **Phase 1 — Foundation & parity.** Stand up the package, `pyproject.toml`,
  Typer CLI, and move the existing pure functions and `ZoomViewer` into
  tested modules. Migrate `calibration_data.csv` to a v2 schema
  (`material`, `substrate` columns) and backfill existing rows as
  graphite / 285nm SiO₂/Si. Graphite `calibrate`/`scan` behave exactly as
  before. Green tree, tests, no behavior change for graphite.
- **Phase 2 — Notion-guided mosaic calibration.** Parse a Notion CSV export,
  scope it to one mosaic/exfoliation session, and drive a guided
  marking flow: the viewer walks the AFM'd flakes one by one (thickness
  pre-shown, matched to the hand-drawn red number on the mosaic), the
  researcher presses F/B, and v2 calibration rows are written tagged
  `material=hBN`, `substrate=...`. No thickness retyping; correct scan-domain
  color.
- **Phase 3 — hBN detection end-to-end + improvements.** Scan an hBN mosaic
  using the imported hBN calibration with a per-scan target thickness band.
  Add **data-driven per-channel weighting** (down-weight/drop channels whose
  calibration contrast is high-variance or near-zero — generalizes G>R>B
  automatically per material) and **local substrate sampling** (coarse
  substrate-color field to handle illumination falloff for edge flakes).
  Validate on chip A; tune `min-area` for mosaic pixel scale.

The calibration "database" stays a single CSV (v2 schema) queried with
pandas by material + substrate + thickness — enough for "grow over time and
query by material/thickness/substrate" without introducing SQLite yet.

  `pyproject.toml`.

### 2. Data models

**File**: `src/flake_scanner/models.py` (new)

Dataclasses replacing the ad-hoc dict records:
- `CalibrationRecord` — material, substrate, filename, thickness_nm,
  flake RGB, sub RGB, contrast RGB (+ optional source/date/flake_id).
- `Candidate` — rank, score, area_px, bbox, centre, mean RGB.
- `MaterialSignature` — per-(material, substrate, thickness-band) mean/std
  contrast plus derived per-channel weights (see §8).

### 3. Color / sampling utilities

**File**: `src/flake_scanner/calibration/sampling.py` (new)

Move and lightly refactor the pure functions from `flake_finder.py`:
`sample_patch()`, `contrast()`, `auto_substrate()` (renamed
`global_substrate()`). Keep behavior identical in Phase 1 (parity); these
get direct unit tests. **Current state**: these live at `flake_finder.py:42-57`
and `46-53`.

### 4. Calibration store (schema v2)

**File**: `src/flake_scanner/calibration/store.py` (new)

- Read/write `calibration_data.csv` with the **v2 schema**: existing columns
  plus `material` and `substrate` (and optional `source`, `flake_id`,
  `exfoliation_date` for provenance).
- `load_signature(material, substrate, tmin, tmax)` — filter rows and return a
  `MaterialSignature` (mean/std contrast + derived channel weights per §8a).
  Generalizes the current `load_calibration()` (`flake_finder.py:346-361`),
  which filters by thickness only.
- **Migration (safe-write)**: old-format files (no `material` column) are
  detected on load and upgraded by backfilling `material=graphite`,
  `substrate=SiO2-285nm`. The migration is **atomic**: validate into a
  canonical v2 dataframe, write to a temp file in the same directory, back up
  the original to `calibration_data.csv.v1.bak`, then `os.replace()` the temp
  over the original. A failed/partial migration leaves the original intact.

### 5. Viewer

**File**: `src/flake_scanner/viewer.py` (new)

Move `ZoomViewer` (`flake_finder.py:61-264`) essentially as-is (keyboard/
trackpad controls unchanged). Add one capability for guided calibration: an
optional **context banner line** showing the current target's label and
thickness (e.g. "Flake A3 — 100 nm — find red '3' on the chip"). Pure
coordinate helpers (`img_to_screen`, `centre_img_coords`) get unit tests; the
interactive loop is left untested (documented as coverage debt).

### 6. Image I/O

**File**: `src/flake_scanner/io/image.py` (new)

- `load_image()` wrapping `cv2.imread`. To preserve bit depth, TIFF inputs are
  read with `cv2.IMREAD_UNCHANGED` (otherwise `cv2` silently downconverts
  16-bit to 8-bit before we can act); the loader then checks `dtype`/`ndim` and
  promotes grayscale→BGR if needed.
- **Analysis image kept in native integer dtype; float only per-strip/patch.**
  The full-resolution analysis image stays in memory as its native dtype —
  `uint8` for 8-bit inputs, `uint16` for 16-bit TIFFs — **never a full-res
  `float32` array** (an 18000×16000×3 float32 image is ~3.2 GiB, the exact
  allocation the strip pipeline exists to avoid). `uint16` preserves the
  sub-256-level precision at half the memory of float32. Casting to `float32`
  happens **only per mask-processing strip** (as `build_mask` already does) and
  for the small sampled patches in `sample_patch()`, so 16-bit differences
  survive into `contrast()` without ever materializing a huge float array.
- **8-bit display array is lazy.** The viewer (`cv2.imshow` needs `uint8`) and
  the annotated report get an 8-bit version, materialized **only when the
  viewer/report is actually opened**, not on every load (a headless `scan` of a
  `uint8` mosaic needs no separate display copy at all).
- **Never per-image min-max on the analysis path.** `cv2.normalize(NORM_MINMAX)`
  subtracts an image-specific minimum — an additive shift that `(S − F) / S` is
  *not* invariant to, which would make calibration and scan mosaics produce
  incompatible signatures across sessions and defeat cross-session reuse. Any
  16-bit→8-bit *display* conversion uses a **fixed multiplicative** scale
  (`img / 65535 * 255`); per-image min-max is allowed only for a
  brighten-for-viewing preview, never for the array fed to `contrast()`.
- **Parity note**: existing 8-bit inputs stay `uint8` end-to-end with the same
  values as today, so `contrast()` outputs are identical — graphite parity
  holds.
- A **lossy-format warning** is emitted when the analysis input is JPEG (the
  hBN mosaics currently are — precision caveat).
- **Pixel scale**: the primary source is a CLI flag `--pixel-scale <µm/px>`
  (used to set `min-area` defaults). As a convenience, when the input is a
  `.tif/.ome.tif`, read pixel-scale metadata via **`tifffile`** (named
  dependency; parses OME-XML `PhysicalSizeX`/`PhysicalSizeY` in µm) and use it
  unless the flag overrides. `cv2` cannot read this metadata, hence the
  separate reader. Non-TIFF inputs (the current JPEG mosaics) rely on the flag.
- `report.py` (new): annotated-image + `candidates.csv` writer, moved from the
  tail of `run_scan()` (`flake_finder.py:474-499`).

### 7. Notion importer & guided calibration (Phase 2)

**Files**: `src/flake_scanner/calibration/notion.py` (new),
`src/flake_scanner/calibration/guided.py` (new)

- `notion.py` — parse a Notion CSV export (columns `Flake ID, AFM,
  Date of Exfoliation, Notes, Quality, Size (nm), Thickness (nm), Usable,
  Used`). Produce a worklist of `(flake_id, chip, thickness_nm,
  exfoliation_date)`. **Handle non-unique Flake IDs** (the same label "A1"
  recurs across exfoliations, and there is **no chip column** — the chip
  letter is the alphabetic prefix of `Flake ID`, so `chip = re.match([A-Za-z]+, flake_id)`).
  Session selection is **unambiguous or it aborts**:
  - `import-notion` **requires both** an exact `--exfoliation-date` (the
    session key) **and** an explicit `--chip <letter>`; the worklist is the
    rows matching **both** `exfoliation_date == key` **and**
    `chip(flake_id) == letter`. `--chip` is validated against the chip letters
    actually present in the CSV (abort if the given letter matches no rows), so
    the selection is fully deterministic — no basename-derived guessing.
  - If that filter yields **zero** rows, or if the surviving `flake_id`s are
    **not unique** within the session (indicating the key is too coarse),
    abort with a message listing the ambiguous rows — never guess.
  - Before writing any records, print the selected count + flake IDs and
    require user confirmation that it matches the flakes marked on the mosaic.
  This is pure logic → well unit-tested (including the abort paths).
- `guided.py` — drive the flow: load the mosaic, iterate the worklist, for each
  entry open/position the viewer with the thickness banner, collect the F/B
  marks, compute contrast via §3, and append a v2 `CalibrationRecord`
  (`material`, `substrate` supplied once per session). Skippable per flake
  (Q to skip). Saves incrementally like the current calibrate loop.

### 8. Detection pipeline

**Files**: `src/flake_scanner/detection/substrate.py`,
`detection/mask.py`, `detection/scoring.py`, `detection/pipeline.py` (all new)

The detection modules are **created in Phase 1 as verbatim ports** of the
current script (so the package `scan` works and graphite parity holds before
`flake_finder.py` is removed), then **modified in Phase 3** to add weighting
and local substrate. Split explicitly:

**Phase 1 (verbatim port — no behavior change):**
- `substrate.py` — `global_substrate()` = today's `auto_substrate()`
  (`flake_finder.py:46-53`), unchanged.
- `mask.py` — `build_mask()` (`flake_finder.py:363-404`) ported exactly,
  including today's strip logic and unweighted Euclidean distance.
- `scoring.py` — `score_region()` (`flake_finder.py:406-410`) ported exactly
  (uniform-channel distance modulo `std`).
- `pipeline.py` — orchestrates load → global substrate → mask → contours →
  score → report, reproducing `run_scan()`'s body (`flake_finder.py:412-499`).

**Phase 3 (enhancements — intentional behavior change):**
- `substrate.py` — add **local substrate sampling**: compute only a **coarse
  downsampled grid** of local median substrate colors and keep it at grid
  resolution; interpolate the needed substrate values **per strip** inside
  `build_mask` (bilinear over the strip's row band). **Never allocate an
  H×W×3 field** (would be ~3.2 GiB float32 at 18000×16000). Global substrate
  remains the fallback when local sampling is disabled or has too few clean
  substrate points.
- `mask.py` / `scoring.py` — switch from uniform Euclidean distance to the
  **weighted contrast distance** defined in §8a, using weights derived from
  the `MaterialSignature`. Also fix the strip **guard rows to be symmetric**:
  process `[write_start - overlap : write_end + overlap]` (clamped) and copy
  back only `[write_start : write_end]`, so morphology at both the leading and
  trailing edge of every strip sees neighbor rows (the current code overlaps
  only forward, leaving a seam at each strip's top edge).

### 8a. Weighted contrast-distance contract (Phase 3)

Shared by `mask.py` and `scoring.py` so both agree exactly:

- **Channel order**: BGR (OpenCV-native), fixed everywhere.
- **Per-channel raw weight** (SNR-style) from the `MaterialSignature` over its
  calibration rows: `r_c = mean_c² / (std_c² + var_floor)` for channels that
  pass the signal gate, else `0`. This genuinely rewards large signal
  magnitude (`mean_c²`, numerator) and penalizes noise (`std_c²`,
  denominator). `var_floor = 1e-3` (contrast units²) prevents divide-by-zero
  and caps the weight of near-constant channels. **Signal gate**: a channel is
  dropped (`r_c = 0`) if `|mean_c| < min_signal` (default `0.05`) — this is how
  graphite's blue channel falls out and green dominates, with no per-material
  code.
- **Normalization to mean-weight-1**: let `K` = number of surviving (gated-in)
  channels; set `w_c = K · r_c / Σ_j r_j`, so `Σ_c w_c = K` and the **mean
  surviving weight is 1**.
- **Distance**: `d(pixel) = sqrt( Σ_c w_c · (contrast_c − mean_c)² )`. With
  `Σ w_c = K`, this reduces **exactly** to the legacy unweighted Euclidean
  distance over `K` channels in the uniform case (all `w_c = 1`), so it is on
  the same scale as today's metric rather than a shrunk RMS.
- **Tolerance**: because the scale matches the legacy metric in the uniform
  case, the current `0.15` default is the **starting point**, but the weighted
  metric is not identical for non-uniform weights, so Phase 3 **re-validates
  and tunes the tolerance against the graphite acceptance boundary** (reproduce
  the current graphite detection set) and sets the hBN default empirically.
  The tolerance is not assumed to transfer unchanged.
- **Degenerate guards**: if all channels are gated off (no informative
  channel) or the signature has fewer than **`min_samples = 3`** calibration
  rows, abort the scan with a clear error rather than emitting garbage.
  `NaN`/zero `std_c` is absorbed by `var_floor`; `Σ_j r_j = 0` triggers the
  all-gated-off abort.

### 9. CLI

**File**: `src/flake_scanner/cli.py` (new)

Typer app with explicit flags replacing `sys.argv`/`input()` prompts:
- `calibrate --image <path> --material <m> --substrate <s>` — manual F/B
  calibration (Phase 1 parity path).
- `import-notion --notion <csv> --image <mosaic> --material <m> --substrate <s>
  --exfoliation-date <d> --chip <letter>` — guided mosaic calibration
  (Phase 2). Both `--exfoliation-date` (session key) and `--chip` are
  **required**; the command aborts on an ambiguous or empty session selection
  (see §7).
- `scan --image <mosaic> --material <m> --substrate <s> --min-thickness <nm>
  --max-thickness <nm> [--tolerance --min-area]` — detection (Phase 3);
  target thickness is per-scan (user decision), with sensible defaults noted
  but nothing hardcoded per material.

The interactive `ZoomViewer` remains interactive; everything else moves to
flags.

## Technical Considerations

- **Pattern Usage** (ARCHI.md): preserve relative-contrast-over-absolute,
  strip-based processing for large images, and calibration-as-growing-asset.
  Material-specific behavior stays in *data* (the calibration DB + derived
  weights), never in code branches.
- **Calibration Data Impact**: schema goes v1→v2 (`material`, `substrate`
  added). Existing graphite rows are backfilled `graphite` / `SiO2-285nm`;
  old-format files auto-upgrade on load. `load_signature()` filters by
  material + substrate + thickness.
- **Detection Accuracy**: Phase 1 must be behavior-preserving for graphite —
  re-validate scan output on an existing graphite mosaic (e.g.
  `D_Full_06_19.png`) against current results before/after the port. Phase 3
  channel-weighting and local-substrate changes *intentionally* shift results;
  re-validate graphite still detects its ~55-flake set and sanity-check hBN on
  chip A.
- **Memory/Performance**: full mosaics ~8400×8400 (hBN JPEG) up to
  18000×16000 (graphite). Keep the strip bound in `mask.py`. Local substrate
  is stored only at coarse grid resolution and interpolated per-strip — a
  full-resolution H×W×3 substrate field (~3.2 GiB float32 at 18000×16000) is
  explicitly disallowed. Strip guard rows become symmetric (§8) so the memory
  bound holds without reintroducing seams.
- **Image Format Handling**: the **hBN mosaics are JPEG** — compression
  artifacts reduce color precision. The pipeline must still run on them, but
  the plan flags re-exporting mosaics as PNG/OME-TIFF from NIS-Elements as the
  accuracy path, and `load_image()` warns on JPEG analysis input. OME-TIFF
  pixel scale, when present, sets `min-area` defaults.
- **Material-Agnosticism**: no `if material == "graphite"` branches. Channel
  weighting is derived from calibration statistics; color signatures come from
  the DB.
- **Edge Cases**: no calibration rows for the requested material/substrate/
  thickness (clear error, don't silently fall back to another material);
  non-unique Notion Flake IDs (scoped worklist + user confirmation); burned-in
  red annotations on mosaics (calibration marks clean pixels; scanning may
  raise red false-positives but red is far from hBN's signature — note as a
  known limitation, prefer clean mosaic exports for scanning); empty/corrupt
  images (e.g. the 0-byte `B_Full.jpg`); flakes near chip edges (local
  substrate).

## Type Definitions

`CalibrationRecord`, `Candidate`, `MaterialSignature` (§2). `MaterialSignature`
carries per-channel weights so scoring and mask-building share one derivation.

## Performance & Cost Impact

Strip-based memory bound preserved. Local substrate field is coarse
(downsampled) → negligible overhead. Weighted distance is the same
per-pixel cost as the current Euclidean distance. No new heavy dependencies
in this feature (scikit-learn deferred).

- Calibration CSV auto-migrates v1→v2; existing graphite data preserved.
- Graphite `calibrate`/`scan` reach behavior parity in Phase 1 before
  `flake_finder.py` is removed.
- CLI surface changes (flags instead of prompts) — README updated; this is a
  local lab tool with no external consumers, so no deprecation window needed.

## Test Impact

- **New unit tests** for pure logic: `contrast()`, `sample_patch()` (edge
  clipping), `global_substrate()` / local-substrate on synthetic images,
  `score_region()` weighting, `load_signature()` filtering + v1→v2 migration,
  Notion CSV parsing + non-unique-ID worklist scoping, and viewer coordinate
  helpers.
- **Integration check**: `build_mask()` on a small synthetic multi-strip image
  (no seam artifacts, symmetric guard rows); a graphite scan parity check
  (Phase 1) and an hBN guided-import → scan smoke test on a fixture crop of
  chip A (Phase 3).
- **Image I/O**: a 16-bit TIFF fixture confirming `IMREAD_UNCHANGED` and a
  **native `uint16`** analysis image (guards against silent `cv2`
  downconversion and against 8-bit quantization on the analysis path) — the
  fixture encodes a flake/substrate difference finer than one 8-bit level
  (`<257` counts) that must survive per-strip/per-patch float conversion into
  `contrast()`. Plus a **contrast-invariance test**: the same scene at 8-bit vs
  16-bit vs constant-scaled must yield equal `contrast()` values, proving the
  analysis path is multiplicative and never shifts the zero point.
- The interactive viewer loop and guided-flow I/O are left untested →
  `docs/4-unit-tests/COVERAGE-DEBT.md` entries with escape plans.
- Fixtures are small synthetic/cropped images — never the full multi-hundred-MB
  mosaics.
